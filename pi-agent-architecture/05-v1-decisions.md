# V1 Scope and Decisions

## Accepted decisions

1. Architecture is language/framework/ORM neutral. No implementation language has been selected.
2. The current repository is a proof of concept. Existing code and APIs may be fully rewritten.
3. Polling is used; public IP and inbound GitHub webhooks are not required for V1.
4. Polling uses the GitHub REST API; the default interval is 60 seconds per repository (configurable). Authentication across the whole installation uses fine-grained GitHub PATs.
5. Issue assignment to the bot is not a V1 prerequisite or trigger. Assigning or unassigning the bot on an Issue does not start or stop work.
6. Issue commands require a bot mention and a recognized slash command in the same comment. Only the original (unedited) comment version is parsed; the command must be the first non-empty line; bot-authored comments never trigger commands; one command directive per comment.
7. Base command requirement: GitHub Write permission. The allowlist is enabled by default and is seeded with the repository owner's account only; a non-empty allowlist additionally requires membership, and an explicitly emptied allowlist falls back to the Write-permission baseline. Configuration lives in repository configuration.
8. Removing a user from the allowlist or revoking their permission does not interrupt an already-running Task; later commands from that user are rejected.
9. One Workflow per root WorkItem in V1. An Issue and its related PR are separate WorkItems/Workflows, with an explicit relationship record.
10. Per-Workflow invariant: a Workflow holds at most one unfinished Task (further same-Workflow commands are rejected at admission). A global cap `max_concurrent_runs` (default 10) in the Orchestrator configuration bounds the total number of concurrently running Runs across Workflows; extra work waits in the durable FIFO queue.
11. A new Pi session and task-specific workspace are created for each Task; every Run attempt uses a new Pi session.
12. A Run represents one execution attempt. A retry creates a new Run and a new Pi session; workspace reuse follows task-type policy (a coder Task continues its agent branch; a reviewer always gets a fresh workspace); a new Task never reuses another Task's session.
13. Agent Profiles are independently configurable and versioned: Docker image, Pi settings, prompt, skills, MCP servers, tools/capabilities, environment references, and resources.
14. Coder pushes directly to the original repository on `agent/issue-<number>` (fine-grained GitHub PAT with write access, dedicated bot-account commit identity, force push forbidden) and reports the result in the Issue before implementation Task completion. The coder phase is enabled later (see decision 36).
15. Automatic PR creation by coder is not assumed in V1; it remains a separate decision/command/configuration.
16. Reviewer receives a fresh workspace at a specific PR Head SHA, separate from coder workspace, read-only where possible.
17. Initial PR review is triggered when the bot is requested as reviewer — exactly one automatic initial review per PR/Workflow lifetime. A review Task pins the PR Head SHA at creation (`target_head_sha`); SHA drift before a queued Task starts cancels it, and removing the review request before execution cancels the not-yet-started Task. Subsequent reviews are manual via `/review`; a new commit alone does not trigger a review.
18. Containers stop after Task completion; the task workspace directory and per-Run `pi-session/` and `logs/` remain on persistent host storage (under `/var/lib/pi-agent/workflows/{workflow_id}/`) until retry/continuation or root cleanup.
19. PostgreSQL stores metadata/orchestration state; session and workspace files are stored on persistent Docker-host storage in V1.
20. Closing a root Issue/PR triggers cleanup of its containers and the Workflow storage tree (workspace directories, Pi sessions, run logs); DB history remains with deletion/cleanup flags.
21. Closing an Issue does not implicitly close/clean its related PR Workflow; each root is handled independently.
22. Reconciliation checks active containers/runtime state. Runtime heartbeat and task progress are separate signals.
23. The 60-minute idle timeout triggers on the absence of ALL observable activity while the container is alive (heartbeat keeps running as a separate liveness signal). It is configurable and initiates reconciliation; it does not map to `TimedOut`.
24. File/object storage and parallel execution are future enhancements.
25. GitHub Projects are out of scope for V1,
26. `/code` replaces `/proceed`: the command approves the latest successful plan Artifact and starts the coder Task against it. Plan iteration is comment-driven: the user answers plan questions as ordinary comments and reruns `/plan`; the new planning Task reads the Issue description plus all comments. No `/plan-continue`-style aliases (considered and dropped): users repeat `/plan`//`/code`.
27. `/retry` repeats the last failed Task of the Workflow as a new Run with a new Pi session; `attempt_number` is incremented by the Orchestrator. There are no admin HTTP endpoints for task management in V1 (amended by decision 65): `/retry` and task cancellation flow only through the GitHub command path.
28. Automatic retries are limited: only transient infrastructure errors, only before the Run starts executing; defaults `max_automatic_retries = 1`, `initial_backoff = 30s`, configurable. Policy levels: `AgentProfileVersion.retry_policy` default → Repository override → effective policy pinned on the Task.
29. The Orchestrator publishes system notifications to GitHub through the Outbox when a Task finally fails (including retries exhausted and `TimedOut`) and when `/stop` cancels Tasks; root-closure cleanup is silent. Agent-owned GitHub writes go through GitHub MCP and never through the Outbox.
30. Independent execution limits: `idle_timeout` 60 min (no observable activity while the container is alive; triggers reconciliation, never `TimedOut`), `max_run_duration` 4 h (wall clock; the Run ends `TimedOut`), `startup_timeout` 10 min (the Run fails with `startup_timeout`). All configurable; `permission_blocked` resets no timers.
31. A review Task pins the PR Head SHA at creation; SHA drift before a queued Task starts cancels it (`review_head_changed_before_execution`); removing the review request before execution cancels the initial review Task (`review_request_removed_before_execution`).
32. Artifacts are stored inline in PostgreSQL and delivered through the next Task's input; artifacts are immutable; limits 256 KiB per artifact / 512 KiB per Task input; formats `markdown`, `json`, `text` only (no `file_reference`).
33. Callbacks are emitted by the Runtime Bridge inside the agent container (launches Pi `--mode rpc`, reads JSONL events, posts events / 30 s heartbeat / completion / failure to the Runtime API). No Pi extension in V1.
34. Unattended permission policy: a per-profile allow-list of tools/MCP operations; denied operations are rejected immediately (fail-closed); no interactive permission dialogs; `permission_blocked` is a RunEvent.
35. V1 runs on exactly one configured execution host; profile images are built locally per profile version (tag `agent-<profile>:v<n>`, local Docker image store, no registry); only `ready` versions are selectable; a missing/unready image rejects the command (`agent_image_not_ready`).
36. Rollout phases: phase 1 ships only the Planner profile with `/plan`, `/status`, `/stop`, `/help`; `/code`, `/review`, and `/test-cases` are enabled when their profiles are configured. `/debug` was removed entirely; no `debugger` profile exists.
37. Agent containers have no host shell access (no host-bridge capability).
38. Queue: single FIFO by `available_at` then `priority`; `/stop` is handled immediately outside the queue.
39. Comment sync: edits update the stored body; deletions create tombstones excluded from future context; `AgentCommand.source_body_snapshot` freezes the parsed text; command grammar — first non-empty line, exactly one directive, bot-authored comments ignored.
40. A merged Pull Request is treated as a closed WorkItem for lifecycle and cleanup purposes; no separate merged event.
41. AgentCommand statuses drop `waiting`: queue waiting is expressed by Task/OrchestrationJob states, human waiting by `Workflow.status = waiting_for_human`.
42. Successful publication of mandatory results to GitHub is a precondition for Task `succeeded` for every agent type (planner — plan/questions; coder — push + result summary; reviewer — review + inline comments; test-designer — scenarios). The agent retries transient GitHub/MCP failures within the Run, verifying GitHub before re-posting to avoid duplicates; otherwise Run/Task fail with `error_code = github_publication_failed` (artifacts are kept), the Orchestrator posts a system notification via the Outbox (it never re-publishes the agent's result), and `/retry` is the recovery path.
43. Run logs are captured by the Runtime Bridge into a per-Run directory on persistent host storage (`stdout.log`, `stderr.log`, `bridge.log`), created and mounted by the Runtime API; size limit 50 MiB per Run (configurable, with rotation); retained until root cleanup and deleted together with session files; `Run.log_storage_reference` points to them; content is not copied into PostgreSQL.
44. The Runtime API exposes a single Run-scoped start endpoint (`POST /internal/runtime/runs/{runId}/start`). Orchestrator owns the AgentSession/Workspace DB rows (Session `provisioning` per Run; Workspace created on the first Run and reused by retries); the Runtime API provisions physical resources and returns runtime metadata. No separate create endpoints.
45. Mention-only dispatch is decided: NO. A bot mention without a recognized slash command never triggers work; the comment stays context. A future conversational mode may arrive via an explicit `/respond`//`/ask` (mention-only dispatch may be considered later).
46. No `/reply` command in V1: the reviewer answers existing review threads as part of `/review`; arbitrary thread replies without starting the reviewer are future work.
47. Coder PR creation is not in V1; the preferred future path is an explicit `/create-pr` command (an explicit user action), not implicit profile configuration.
48. `/test-cases` targets Issues only in V1; a PR target is rejected with a clear explanation. PR support may be added later when a diff/Head-SHA-based test-design scenario is defined.
49. Allowlist: enabled by default, seeded with the repository owner's account only. A non-empty allowlist requires Write permission AND membership; an explicitly emptied allowlist disables list filtering, leaving the Write-permission baseline. Configuration lives in repository configuration.
50. The whole integration uses fine-grained GitHub PATs (no GitHub App in V1): a read-only PAT for the Poller/sync and write-capable PATs for agent MCP/Git operations, both repository-scoped. This supersedes the earlier GitHub App installation-token suggestion for coder push; the commit identity is the dedicated bot account owning the write PAT.
51. Issue↔PR links come from GitHub timeline events synced by the Poller: a closed event whose commit carries closes/fixes semantics → relation `closes`; a cross-referenced event → relation `related_to`; branch naming (`agent/issue-<n>`) is a hint only, never a standalone basis. If GitHub reports no explicit link, none is created; V1 has no manual link management.
52. Storage layout: plain directories on persistent host storage, not named Docker volumes — `/var/lib/pi-agent/workflows/{workflow_id}/tasks/{task_id}/workspace` and `.../runs/{run_id}/{pi-session, logs/{stdout.log, stderr.log, bridge.log}}`; UUID-based names; containers mount what they need. Backups: PostgreSQL and profile configuration only; workspace/session/log backups are an accepted V1 risk. Cleanup: root closure deletes the Workflow storage tree after containers stop; no age-based cleanup of open Workflows; periodic reconciliation removes orphaned directories.
53. Polling parameters: GitHub REST API; default interval 60 s per repository; page size 100 with `Link` headers; 5-minute overlap window for timestamp queries; per-repository/per-stream cursors (endpoint families: issues, pulls, issues/comments, pulls/{n}/reviews, pulls/{n}/comments, issues/{n}/timeline); a cursor advances only after durable save; deleted comments are discovered via a daily full sweep of known IDs; review requests pending an initial review are rechecked each cycle. Rate limits: `ETag`/`If-None-Match` conditional requests (304 does not consume the primary limit; 5 000 req/h baseline); `403`/`429` honor `Retry-After`/`X-RateLimit-Reset`; secondary limits use bounded exponential backoff.
54. Profile configuration is YAML in Git — `agents/<profile>/profile.yaml` plus Dockerfile, `prompts/`, `skills/` (runtime/image, prompt and skills references, MCP servers/tools, permission allow-list, resource limits, retry policy, startup/idle/execution timeouts, secret references). Creating an `AgentProfileVersion` pins the Git commit SHA, a configuration snapshot, and file hashes; any configuration change creates a new version. Secrets live in host-managed files (e.g. `/etc/pi-agent/secrets/`), referenced by name in YAML and mounted read-only in-container at `/run/secrets/<name>`; least-privilege per profile; secrets never travel via env vars or image layers.
55. Configuration plane (V1): desired configuration is YAML in the system repository — `config/system.yaml` (global settings incl. `github.bot_login`, command grammar, operational knobs), `config/repositories.yaml` (registered repositories with per-repo allowlists, permitted commands, permitted WorkItem types, authorization policy), `config/routing.yaml` (routing rules: global defaults plus per-repo overrides), `config/agents/<profile>/` (profile.yaml, Dockerfile, prompts, skills). The Config Loader — a startup component of the Orchestrator — validates the configuration, creates/updates Repository/AgentProfile/AgentProfileVersion/RoutingRule records and sync cursors, and checks the bot identity against `GET /user`. Synchronization happens only at application startup/deployment; hot reload, Admin API, CLI, and web UI are out of scope for V1. YAML is the source of desired configuration; PostgreSQL remains the source of runtime state.
56. Agent Profile versions are created only from the configuration plane: creating a version pins its Git commit SHA/config snapshot and triggers an image build executed by the Build Worker on the execution host (local image store, tag `agent-<profile>:v<n>`, no registry); a successful build sets the version `ready`. The image is the sole source of Pi runtime configuration in V1: the Pi version is pinned at build time (floating `latest` is never used; a Pi upgrade means a new AgentProfileVersion), and the profile's Pi configuration (settings, MCP, extensions, skills, prompts, system instructions) is baked read-only at `/opt/pi-agent/profile` and selected via `PI_CODING_AGENT_DIR`. LLM model/provider selection is deferred to V2.
57. Session isolation uses pi's own CLI mechanics: Pi runs with `--session-dir` pinned to the per-Run host directory (`/var/lib/pi-agent/workflows/{workflow_id}/runs/{run_id}/pi-session/`, mounted into the container) and `--session-id <runId>`. `AgentSession.session_file_path` records the actual path discovered by the Bridge. AgentSession is one-shot and 1:1 with its Run (`run_id` unique): never pooled, reassigned, or reused across Tasks/Runs/profiles; a terminated Session never returns to service; recovery after a Runtime restart may reopen the backing files of the same Run only; DB records persist after file deletion with file state tracked separately.
58. Bridge realtime events are read exclusively from Pi's RPC stdout JSONL stream (the session `.jsonl` file is saved history, not an event source; stderr is diagnostics). pi→RunEvent mapping is fixed in 04 §4 (`agent_start`→`agent_started`, `turn_start`→`turn_started`, `turn_end`→`turn_completed`, text deltas→aggregated `assistant_output`, `tool_execution_*`→`tool_started/progress/completed`, `agent_settled`→`agent_settled`). Progress: non-empty text deltas (aggregated before persistence), tool start/update/end, turn completion, artifact creation; heartbeat, thinking deltas, queue updates, and liveness are not progress. Task input is delivered as one RPC `prompt`; never via env vars or mounted input files.
59. Run result contract: the agent writes `result.json` in the Run's writable directory (schemaVersion, summary, artifacts[] with file paths, requiredPublications[] with toolCallId/kind/externalId). The Bridge validates the manifest and files (within the allowed directory), derives branch/commitSha via Git, correlates `requiredPublications` with `tool_execution_end` records, and posts the normalized result via `/completed` — the verification mechanism required by decision 42.
60. Callback security/resilience: fresh random per-Run credential delivered to the Bridge via read-only secret file (never a regular env var, never given to Pi), stored hashed, scoped to that runId's callbacks, revoked after confirmed terminal delivery. Callbacks are spooled durably (`runs/{run_id}/callback-spool/`) before sending; network/5xx/429 are retried with exponential backoff and the same eventId; heartbeats coalesced; lifecycle/terminal callbacks never dropped; after a Bridge restart the spool is redelivered; delivery completes only on Runtime API persistence confirmation, and the next Run for the same Task does not start until the previous Run's termination is fixed.
61. Graceful stop sequence: Orchestrator → Runtime API → Bridge: RPC `clear_queue` first (abort alone can continue queued messages), then `abort`/`abort_bash`, wait up to ~30 s for `agent_settled`, close Pi stdin, SIGTERM then SIGKILL if needed, verify child processes stopped, post the terminal `cancelled` callback.
62. Execution Host Monitor: observer process on the single execution host; it watches session-file activity, process trees/cgroups/containers (Docker API), and managed storage, and posts telemetry to the Runtime API with its own credential. The Bridge observes Pi (heartbeat, RPC/request activity, run/tool events); the Host Monitor observes filesystem/process/container activity. The control plane never reads execution-host filesystem paths or process tables directly.
63. Context Assembler (Orchestrator) + `RunContextSnapshot`: each Run's input is assembled within the mandatory per-profile `max_context_tokens` (must fit the model window with an answer reserve) and the artifact limits (256 KiB per artifact / 512 KiB artifacts total / 512 KiB serialized input), frozen as an immutable snapshot with content hash and included/excluded sources. Pruning priority: never drop the command, mandatory inputs, or the last approved plan; keep recent user answers and unfinished discussions; drop older/less-significant comments; reviewers keep unresolved threads first. No silent truncation: mandatory context that cannot fit prevents the Run (Task fails with `context_too_large`). The Bridge renders the snapshot as one structured Markdown message via RPC `prompt`.
64. Reviewer data plane: Review Tasks pin both `target_head_sha` and `target_base_sha`; the Runtime forms the diff locally via Git while provisioning the workspace (GitHub `pulls/{n}/files` is not the diff source — 3 000-file cap). Reviewer context: unresolved review threads first, then remaining threads with their state/answers/file-line bindings. Full commit history is not synced by the Poller in V1 (head/base SHAs stored; commit metadata read from Git in the workspace; `pulls/{n}/commits` ad hoc only).
65. Internal API security: no public exposure; private network, TLS across hosts; Orchestrator→Runtime API and Host Monitor→Runtime API use dedicated service credentials; Bridge→Runtime API uses the per-Run callback token (decision 60); Bridge tokens cannot start/stop containers; PostgreSQL is not exposed. There are NO admin HTTP endpoints for task management in V1 — `/retry` and `/stop` flow only through the GitHub command path (amends decision 27). PATs: one read-only polling PAT for all configured repositories; one fine-grained write PAT per repository for agents (MCP/Git via profile/repository secret references) and Outbox notifications. Rotation: create with equivalent rights → verify via GitHub API → switch the secret version → revoke the old token after in-flight Runs finish; compromise → revoke immediately (even if active operations break); expiry tracked with a 14-day warning; no automatic fallback to another PAT. A compromised write PAT must not give write access to any other repository.
66. Authorization mechanics: Write permission verified with `GET /repos/{owner}/{repo}/collaborators/{username}/permission` — `write` and `admin` accepted; `maintain` treated as `write`, `triage` as `read`; cached ≤60 s and rechecked at claim when stale; GitHub 404 rejects the command; transient errors (5xx, network, rate limits honoring `Retry-After`/`X-RateLimit-Reset`) leave the command `received` with the check deferred; a PAT lacking auth scope is a system configuration error. `system.yaml` pins `github.bot_login` and validates it against `GET /user` at startup (mismatch = configuration error). The allowlist starts with only the configured project owner (decision 49 unchanged).
67. Outbox delivery policy: transient failures (network, 5xx, 429, rate-limit 403) retry with exponential backoff — max interval 1 h, total window 24 h; permanent errors (401, regular 403, 404, 422) and window exhaustion move the action to a retained `dead_letter` (payload, attempts, last error kept; surfaced in host logs and health status). Duplicate control: the delivered comment carries an invisible HTML-comment marker with the `idempotency_key`; after an ambiguous timeout the Outbox checks existing comments for the marker before re-sending; one dispatcher owns an action at a time via a DB lease. V1 guarantee: at-least-once delivery with best-effort deduplication, not exactly-once.
68. Idle/wall-clock outcomes (refines 23/30): `idle_timeout` (default 60 min — absence of ALL observable activity while alive) makes the Run a reconciliation candidate; the Host Monitor checks child processes/CPU/IO before any stop (long-running builds/tests must not be killed for silence); a confirmed hang fails the Run with `error_code = idle_timeout`; `max_run_duration` (4 h) ends the Run `TimedOut` independently; `startup_timeout` unchanged. `permission_blocked`, thinking deltas, and queue updates are never progress and reset no timers.
69. `permission_blocked` aftermath: the Bridge records the RunEvent, returns an explicit denial to Pi, and never parks a permission dialog. The Run may still succeed if the agent completes mandatory work another way; if a mandatory operation is impossible, the Run fails with `error_code = required_permission_denied`, the Task fails, the Workflow returns to `waiting_for_human`, and the Outbox publishes the notification; a hung agent is handled by the ordinary idle/wall-clock timeouts.
70. Retry semantics (refines 28): automatic retry applies only to transient infrastructure errors before the Run starts executing and transitions the Task `Failed → Queued` only while retry budget remains. After execution began, recovery is manual: `/retry` moves the Task `Failed → Queued` and creates the new OrchestrationJob in one transaction, after which normal claim flow follows with `attempt_number + 1` and a fresh AgentSession. No Run ever starts while the Task is `Failed`; a rejected `/retry` (preconditions, admission, occupancy) leaves the Task `Failed`; `/retry` on a Task whose pinned profile version is `disabled`/not `ready` is rejected with `agent_profile_not_ready` (Task stays `Failed`; the version must be restored or a new Task created).
71. Workflow `Failed` is terminal in V1: it requires manual operator intervention at the data level; only `/status`, `/help`, and root closure remain available. The `Failed → Active: explicit retry/recovery` transition is removed from 03 §1.
72. Mid-run blockers (updates 06 §4): the agent publishes its question via GitHub MCP, checkpoints partial results/changes to the agent branch, and finishes: Run `Succeeded` with `outcome = needs_human_input`, Task terminal `Blocked`, Workflow `waiting_for_human`. The next command creates a new Task/Run with a new Pi session, initializing the workspace from the current agent branch; uncommitted changes are not guaranteed. The coder `base_sha` is captured at first provision, later Tasks continue the existing agent branch, and no automatic rebase onto a moved default branch is performed in V1 (a manual rebase before PR creation may be required — accepted limitation).
73. Root reopen: reopening an Issue/PR does not resurrect its Workflow; it stays `closed`, no second Workflow is created (`UNIQUE(work_item_id)` holds), and commands for the reopened item are rejected — further agent work requires a new Issue/PR.
74. Draft/fork PRs: no automatic initial review while a PR is draft; when it becomes ready for review (bot still requested), the initial review Task is created; explicit `/review` is allowed on a draft PR and the result is marked as a draft review. Reviewer supports fork PRs: checkout from the PR head ref of the base repository at the pinned `head_sha` in a fresh read-only workspace; fork code is untrusted — its scripts/builds/tests are never run automatically; the coder never works against forks; an unavailable head fails the Task with `review_source_unavailable`.
75. Repository pause and cap counting: `Repository.is_enabled = false` is a pause — task-producing commands rejected, polling continues read-only, queued Tasks stay unclaimed, active Runs may finish; `/status`//`/help` remain available; re-enabling resumes processing. `max_concurrent_runs` counts Runs in `Claimed`, `Starting`, `Running`, and `Stopping` (awaiting confirmed stop); the slot is released only at terminal Run state plus confirmed process/container stop; queued/pending work occupies no slot.
76. PostgreSQL retention: no automatic deletion of orchestration history in V1 (Workflows, Tasks, Runs, Artifacts, comments, reviews, events, tombstones, audit kept indefinitely); regular backups and DB size monitoring are mandatory; archiving/partitioning is future work; high-frequency RPC events are aggregated, and stdout/stderr never lands in PostgreSQL.
77. Poller mechanics: the deleted-comment daily sweep is a separate full listing (conversation comments via `issues/comments`, inline per open PR via `pulls/{n}/comments`, page size 100) compared against stored IDs; a missing ID is re-checked by direct request — a confirmed 404 creates a tombstone, 403/rate-limit/network errors never mean deletion; the sweep has its own run state and never advances incremental cursors. Orphaned-storage reconciliation: the Host Monitor scans only `/var/lib/pi-agent/workflows/`; a directory is a candidate when its Workflow/Task/Run no longer exists in PostgreSQL or storage is already marked deleted; candidates persist ≥24 h, are quarantined for another 24 h before physical deletion; nothing is deleted while PostgreSQL is unavailable or active containers/processes use the tree.
78. Normalized GitHubEvent naming: `work_item_created`, `work_item_updated`, `work_item_closed` (with `close_reason = merged` for merged PRs), `issue_comment_created/updated/deleted` (Issue and PR conversation comments), `review_comment_created/updated/deleted` (inline), `pull_request_review_submitted/dismissed`, `review_requested`, `review_request_removed`, `pull_request_synchronized`. `GitHubEvent.source` ∈ {`rest_resource_sync`, `timeline_api`, `snapshot_diff`, `full_reconciliation`}.
79. Editorial/normalization decisions: WorkItemLink V1 relations are only `closes` and `related_to` (`created_from`, `blocks`, `custom` reserved); `AgentCommand.arguments` is `{}` in V1 (trailing comment text is user context for the Context Assembler, not parsed arguments); `Run.result_summary` is a short per-attempt diagnostic while full results live in Artifacts; `/status` renders `Run attempt: #N` (absolute attempt number — automatic and manual retries included; no denominator); the one-unfinished-Task invariant is additionally enforced by a partial unique index `ux_task_one_unfinished_per_workflow` (on `workflow_id` WHERE status IN Queued/Claimed/Starting/Running) plus transactional Task+Job creation with `SELECT … FOR UPDATE` on the Workflow row.
80. No implement-without-plan mode: `/code` always requires a successful plan Artifact (the latest successful planning Task); the repository-configuration exception mentioned in earlier drafts is removed.

## V1 command syntax

Canonical form: `@<bot-account> /<command> [arguments]`. The mention is required in the same comment. `/agent <command>` may be considered as a future alias.

Rollout phases: phase 1 (planner only) enables `/plan`, `/status`, `/stop`, `/help`. `/code`, `/review`, and `/test-cases` become available when their profiles are configured; commands for missing/unready profiles are rejected with `agent_profile_not_configured`.

See [06-command-reference.md](06-command-reference.md) for the full command contract.

| Command | V1 meaning |
|---|---|
| `/plan` | Planner analyzes an Issue, identifies gaps/questions, creates plan Artifact and GitHub comment; then waits for human input |
| `/code` | Coder implements the approved plan (the command approves the latest plan), runs checks, commits and pushes a branch, and reports back; then waits for human input |
| `/review` | Reviewer reviews the pinned PR Head SHA in a fresh read-only workspace and submits review/comments |
| `/test-cases` | Test designer creates test scenarios/cases as an Artifact and comment; it does not implement/run tests |
| `/status` | Reports Workflow/Task/Run/queue status; no Task or container |
| `/stop` | Gracefully cancels the active Task and all queued Tasks for the targeted WorkItem's Workflow; does not close the WorkItem or delete storage |
| `/help` | Publishes commands valid for the target type; no Task or container |
| `/retry` | Repeats the last failed Task of the Workflow as a new Run with a new Pi session; no new Task |

## Explicitly out of scope for V1

- GitHub Projects.
- Webhooks/public inbound networking.
- Parallel task execution.
- Automatic PR review after every commit.
- User-facing dashboard.
- External object/file storage.
- Final security design (but profile capabilities and authorization metadata should be modeled now).
- Language/framework/ORM selection.
- Automatic PR creation by coder unless later explicitly enabled.
- Free-form natural-language comment handling without a recognized command (decided: not in V1; a conversational mode via `/respond`//`/ask` may be a future extension).

## Open decisions

None remain — all former open items are resolved (see decisions 45–54). Future enhancement candidates (not in V1): conversational mode via `/respond`//`/ask`, an explicit `/create-pr`, a `/reply`-style thread command, PR support for `/test-cases`, and a `/agent <command>` alias.
