# Pi RPC API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** HTTP endpoints on `api/` to run pi sessions in per-session containers spawned by Komodo, talk pi RPC over Komodo terminal websockets, answer pi's requests by executing them on the host, and log pi output.

**Architecture:** One Komodo `Deployment` (`pi-session-<id>`, image `pi-worker:latest`, main process = `pi --mode rpc`) per session; the API attaches via a Komodo **attach**-mode terminal websocket (raw byte pipe = pi's RPC stdin/stdout). A hand-written protocol client (modeled on pi's exported `RpcClient`, no new deps) does JSONL framing, id correlation, event buffering, extension-UI handling and logging. The `host-bridge` pi extension (delivered via the shared `pi-agent-state` mount) routes host-side commands through documented `extension_ui_request`/`response` dialogs.

**Tech Stack:** Node 22.9+ (`node:http`, global `WebSocket`, `node:child_process`), existing `komodo_client` ^2.3.2 dependency, pi extension TypeScript file.

**Spec:** `docs/superpowers/specs/2026-11-18-pi-rpc-api-design.md`

## Global Constraints

- No new npm dependencies; api stays raw `node:http` (`server.mjs` style).
- Protocol: strict JSONL, split on LF only, strip optional leading CR, non-JSON lines ignored. Records: `response` (match by `id`), session events, `extension_ui_request`.
- Komodo JSON config field names exactly as `komodo_client/dist/types.d.ts` declares: `DeploymentConfig` = `server_id`, `image: {type:"Image", params:{image}}`, `extra_args: string[]`, `volumes: string` (newline-separated), `labels: string` (newline-separated `key=value`), `restart: "no"` (`RestartMode.NoRestart`), `auto_update: false`.
- Session deployments: name prefix `pi-session-`; id is the name-suffix; terminal name = deployment name.
- Volumes: `pi/pi-agent-state:/home/pi/.pi/agent` and `pi/pi-worker-workspace:/workspace` (shared, per design).
- host-bridge envelope (exact): extension sends `ctx.ui.editor("host-bridge", JSON.stringify({ command }))`; API answers `extension_ui_response { value: JSON.stringify({ exitCode, stdout, stderr, killed }) }`.
- Env additions: `PI_WORKER_SERVER` (default `Local`), `PI_WORKER_IMAGE` (default `pi-worker:latest`), `PI_HOST_BRIDGE_TIMEOUT_MS` (default `60000`), optional `PI_HOST_BRIDGE_CWD` (default `process.cwd()`).
- Engine floor: `node >= 22.9` (global `WebSocket`, `--env-file-if-exists`).

## Review Focus

- A WS binary frame split mid-JSONL-line → lines must reassemble; expect no parse drop. Test: Task 1 framing test.
- Echo/garbage/PTY lines on stdout → ignored, logged, never crash. Test: Task 1 framing test.
- Human dialogs (`select`/`confirm`) must never block prompting; pending list answers late or never. Test: Task 1 pending-queue test.
- `DELETE /sessions/:id` while pi is mid-run: `StopDeployment` then `DeleteDeployment`, exit code from pi's SIGTERM shutdown ignored (session file already flushed per-compaction). Verified live in Task 4.
- Stale registries: sessions created in a previous API lifetime must appear in `GET /sessions` from `ListDeployments` (registry not required to list). Test: Task 2 smoke step 2 after api restart — covered live in Task 4 by listing.

**Interfaces (produces):**
```js
export class PiRpcSession {
  constructor({ komodo, server, container, terminal, logsDir, hostBridge })
  // komodo = KomodoClient instance (for connect_terminal); hostBridge = { cwd, timeoutMs }
  async connect({ initTimeoutMs = 20000 } = {})   // terminal ws + login + get_state handshake → { state }
  rpc(cmd)                                        // {type,...} (no id) → Promise<response record>
  events(since = 0, types = null)                 // → { records: [{seq, ts, record}], nextSeq }
  listPendingUi()                                 // → [{ id, method, payload, receivedAt }]
  answerUi(id, { value | confirmed | cancelled }) // → boolean (sent)
  close()                                         // ws.close(); buffers kept; reconnectable via connect()
  get connected                                   // boolean
  get stateInfo                                   // last get_state result from handshake, or null
}
export function _splitLines(chunk, rest) // exported for tests: (Buffer,string) → { lines, rest }
```

- [ ] **Step 1: Write framing tests** (`api/rpc-session.test.mjs`, `node --test`): frame split mid-line reassembles; CR stripped; non-JSON echo dropped. Assert exact `lines` output for: one JSON per frame; `{"a":1}\r\n{"b":2}` split across two chunks; a garbage `some echo text` line.
- [ ] **Step 2: Run** `node --test api/rpc-session.test.mjs` → FAIL (module missing `_splitLines`).
- [ ] **Step 3: Implement.** `komodo.connect_terminal({ query: { target:{type:"Container",params:{server,container}}, terminal, init:{ mode:"attach", recreate:"Never" } }, on_login, on_message, on_close })` returns the `ws` — keep it. After login: UTF-8 decode + `JSON.parse`; `response`+id → resolve pending (reject after 120 s with `error: timeout`); `extension_ui_request` with `method==="editor" && title==="host-bridge"` → parse `prefill` JSON `{command}` → `child_process.exec(command, {cwd: hostBridge.cwd, timeout: hostBridge.timeoutMs})` → send `{"type":"extension_ui_response","id":<id>,"value":JSON.stringify({exitCode,stdout,stderr,killed})}`; other dialogs → pending queue. Everything else → event buffer (cap 2000, shift). Every raw line logged to `logsDir/<terminal>.log` as `{ts, dir:"out"|"in", line}` via one append write stream. `rpc()` also treats `success:false` responses as resolved (caller inspects). Top-of-file: same `globalThis.localStorage` shim line as `server.mjs` (komodo_client import-time browser touch), with `shortcut:` comment.

  - `GET /sessions/:id` → registry session `rpc({type:"get_state"})`.
  - `POST /sessions/:id/connect` → if not in registry, construct PiRpcSession + `connect()` (container must be running, else 409); → `{ connected: true }`.

  - `GET /sessions/:id/events?since=&type=` (csv filter) → session.events.
  - `GET /sessions/:id/ui` → `{ pending }`; `POST /sessions/:id/ui/:requestId` body `{value|confirmed|cancelled}` → `answerUi`, unknown id → 404.
  - 404 help text lists all routes; existing `/status`, `/start`, `/stop` untouched.
